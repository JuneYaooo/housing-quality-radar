# 报告与增量监控

## 首轮报告

1. **范围与覆盖**：区域/小区、租售条件、观察日期、实际采集入口、查询与排序、帖子/账号/去重房源数、失败和缺失。说明这是首次摸底还是已有纵向记录。
2. **区域基线**：按小区与户型汇总报价和公开状态变化；列样本量和未知状态，不把横截面数据写成成交速度。
3. **账号画像**：公开账号链接、角色及置信度、样本数、关联来源组、信息一致/冲突例证。不要生成未经证实的黑名单。
4. **候选对照**：房源 ID、小区、户型面积、报价与费用、适配状态、真实性状态、独立来源组/账号数、首次/最近观察、性价比结论、下一步核验、原帖链接。先展示最值得核验的少量候选，其余保存到完整记录。
5. **单套证据卡**：支持证据、反证、未知项分别列出；每项关联来源和时间。展示价格及发布历史，有条件时采用简短时间线。
6. **下一步**：例如确认当前可租售、完整费用、未剪辑的连贯室内视频、实际带看、合法授权等。生成可复制的核验问题，但不自行发送。

输出少而有证据；没有达到优先门槛的房源时明确说明，仍可交付待核验清单，不凑数。

## 增量事件

- 新发现：此前未观察到的高置信房源，不称“刚挂牌”。
- 价格变化：同房源、同价格口径、可比费用条件下的新报价。历史误写修正与真实降价分别标记。
- 证据变化：新独立来源、关键冲突出现/解决、用户提供核验结果。
- 状态变化：发布者称已租售、用户核验退出、恢复发布；保留证据等级。
- 抓取故障：登录或访问长期失效需用户行动时通知，不能报“本期无新房”。

重复曝光、同一素材搬运及无实质变化默认不通知。事件引用旧值、新值和证据，按 events 的幂等键防重复。变化后的候选重新经过硬条件和冲突门槛。

## 调度

“做一个监控 Skill”只创建能力；用户随后要求每天/每小时监控时，读取其时区和频率并使用宿主已提供的调度功能。未指定频率可提出每天一次作为建议，不能把建议写成已启动。无调度工具则提供手动运行方式并明确后台未运行，不用持续 sleep 假装后台服务。

已授权建立定时任务时，任务提示必须包含：Skill 路径或名称、watch_id、配置及数据目录、时区、读取历史后增量采集、运行上限、失败记录、仅在实质变化或需用户行动时通知。浏览器需交互登录的任务要记录非交互运行限制；创建成功只代表任务注册成功，不代表数据入口已经可持续访问。使用实际返回的任务标识报告启用状态。

## 检查场景

发布前或规则改动后，用虚构或脱敏数据走以下场景，不访问外部账号、不发消息：

| 输入 | 应有行为 |
|---|---|
| 同门店 8 个号一天内发同一图片 | 多账号传播，独立来源不按 8 计；不单凭此升为优质 |
| 两个独立中介字段一致，只有精修图 | 可有交叉支持，但当前可用和实物核验仍未知 |
| 90 天内重复卖同一套高总价住宅 | 记录长期曝光，结合可比基线核验，不能直接判假 |
| 房帖删除或搜索不到 | 状态未知，不能计成交 |
| 同公寓样板间相同、不同房号库存 | 素材同源，不能强行合并为一套 |
| 月租 3500 元另有必付月服务费 800 元 | 已知必要月成本至少 4300 元，不能按 3500 排名 |
| 仅三套可比房、其余是重复发布 | 展示三套对照，不能宣称有充分样本的价格优势 |
| 采集遭遇验证码或账号退出登录 | 保存 partial/blocked，通知需要操作，不绕过 |
| 同轮任务重跑且无新证据 | 不产生重复提醒；失败恢复不覆盖历史 |
| 用户只说帮我做一个 Skill | 完成 Skill，不虚构真实房源、不自行启动调度 |

来源适配验收：浏览器已成功时不重复调用 TikHub；仅健康检查成功不标业务可用；同帖来自两入口只算一个帖子；读取昨日缓存不刷新今日可用时间；mc 匿名输出不增加已知独立来源数；opencli user 不能误换成 creator-profile；来源限额不足时保存部分进度。

报告实际启用/离线降级、shadow 模式、请求与实际模型、调用数、复核数、失败和未处理数。费用仅根据当期定价和实际 usage 估算；缺 usage 时写未知。不能把 API 延迟说成完整采集和推荐耗时，也不能以分类高置信替代证据。
